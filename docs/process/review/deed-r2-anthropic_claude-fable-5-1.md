## 3. Track choice and crowding
`nfts` is correct and probably the least crowded "money" track — most entrants will do membership-club clones from the prompt, dynamic-metadata NFTs, or ERC-6551-style "NFT points to wallet" ports. Few will touch TLA because there's no SDK; a working, tested TLA build has a real moat. Keep `nfts` lead. Add `agents` (agent earns via x402, pays for inference) and `security` (capped grants, revocation, attack harness, fail-closed runtime) to the `tracks` array — the harness is arguably stronger as a security artifact than as an NFT artifact. Don't add `open`; it dilutes.

## 4. Three biggest weaknesses
1. **The asset has no plausible buyer.** The whole premise ("value = name + reputation + earnings stream") is asserted, never demonstrated. A judge who asks "show me why someone pays more than the rent for `scout.<tla>`" gets nothing. The membership-club example in the prompt at least has an obvious buyer; you've replaced it with something weaker.
2. **The transfer guarantee is weaker than claimed.** "Protocol rejects the seller from that block on" is true for owner-authority calls, but a spend grant already issued to the seller's extension key may remain valid after `nft_transfer` unless the TLA contract explicitly invalidates grants on owner change (verify this). Your mitigation for out-of-band transfers — "the runtime re-checks ownership" — only constrains an *honest* runtime. A malicious seller's runtime with a still-live grant drains up to the budget until the buyer revokes. If TLA doesn't clear grants, your "use old spend grant → fails" harness case is false, and the precise claim in the README is wrong.
3. **Handover is an off-chain state machine, not a contract.** Freeze → drain → revoke → sweep → list → observe → regrant is seven steps across two parties and an RPC; any step can wedge (seller disappears after listing, buyer never grants, RPC lag). Judges reading "sale in the middle of a payout" will probe for the race. An atomic on-chain handover would be a real contribution; a scripted sequence is a demo.

## 5. Changes to reach 9+
1. **Atomic handover contract (`deed-escrow`).** One `buy(name)` call: cross-contract promise chain that (a) view-checks no active grants on the TLA account (or revokes them as current-owner-approved operator), (b) `nft_transfer`s the name to buyer, (c) pays the seller, (d) installs the buyer's spend grant for the buyer-supplied extension key — all or nothing. Mid-payout sale becomes a one-block question answered by the receipt order, not a drain procedure. This turns your weakness #3 into the headline NEAR-only feature (promise-based atomicity across NFT + account + grant).
2. **Close the grant gap in the contract, not the runtime.** If TLA keeps grants across owner change, write a tiny "guardian" extension that stores `granted_by_owner` and refuses any grant whose issuing owner ≠ current `w_resolve_auth` owner. Show the diff. Now the harness case "old spend grant" fails *cryptographically*, and the README claim becomes true for out-of-band transfers too.
3. **Make the seller never hold the key.** Run the service runtime as a Shade Agent / TEE worker whose extension key is generated inside the enclave and registered by code hash; the Deed owner only authorizes a code hash. On sale, the buyer re-points the Deed to their own enclave (or keeps the same one — it's attested). Then "we don't claim the seller forgets anything" disappears: there is nothing to forget. If 12 days is too tight, ship the attestation check on inference only and document the worker-key design with a stub — but at least one attested component beyond "NEAR AI Cloud signed the answer."
4. **Give the asset a buyer.** Replace or augment the explainer with something where the *name and track record* obviously compound: e.g. a `wallet-reviewer.<tla>` that audits NEAR contracts/transactions for a fee and whose on-chain evidence ledger (jobs, refunds, TEE-attested model, dispute rate) is the price signal. Ship two Deeds with divergent ledgers and show the marketplace pricing them differently. Get three real external payments before submission and label them.
5. **Ship the prompt's gated page and holder history literally.** Owner-only operator console (opens only if `w_resolve_auth` resolves to the connected wallet) + per-Deed timeline: holders, earnings, payouts, grants issued/revoked, attacks rejected. Make the harness output *part* of this history so the buyer sees "seller tried 5 times post-sale, all refused" as on-chain receipts in the UI.
6. **Reproducibility for AI screeners.** `make demo` that spins a local/testnet TLA name, runs the harness, and emits a JSON report with receipt IDs and failure reasons. Cite the exact TLA contract account IDs and method ABI you call in the README; screeners will try to verify.
7. Optional one-liner, not a feature: the buyer's owner account uses an ML-DSA-65 key — "the Deed can be held by a post-quantum account; the TLA layer doesn't care." Cheap, true, on-theme for 2.13/2.14. Don't spend more than an hour.

## 6. Factual / technical issues
- **Function names unverified.** `hos_grant_spend(extension, receivers, budget, tokens, expires_at)`, `w_resolve_auth`, `hos-wallet` are stated as fact. There is no SDK; confirm every signature against the deployed contract ABI before writing the README. If they differ, the "verified" section is a liability with screeners.
- **"Protocol rejects the seller from that block on"** — only for owner-gated calls. Outstanding grants/keys are a contract-design question, not a protocol guarantee. Rephrase or prove it.
- **"List on the TLA marketplace (Intents)"** — presence of a live TLA marketplace settling via NEAR Intents is asserted, not verified. If absent, you need your own sale contract (which is change #1 anyway).
- **x402 via PingPay** — x402 is an HTTP 402 payment flow; NEAR-side facilitator support and PingPay's role should be confirmed and named precisely. If it's a thin wrapper, say so; don't let "x402" carry weight it doesn't have.
- **TEE-signed responses prove the model, not the service.** NEAR AI Cloud attestation covers inference; the seller's runtime can still serve wrong/cached answers. Don't imply end-to-end verifiability unless the runtime is also attested (change #3).
- The ML-DSA/universal-account facts are correct as stated but unused; they add nothing to this submission as written — either use them (item 7) or drop the section.
- "Transfers outside Deed fail closed" is an honesty property of *your* runtime, not a security property. State it as such.
